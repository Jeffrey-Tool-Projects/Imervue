## U-20261126-02 · 2026-11-26 · Stop deletes from freezing the window · #fix #performance #delete

- **What**: the soft delete itself only hides files in memory. The freeze came from what ran on the GUI thread afterwards. (1) Every folder poll after a delete re-listed and re-sorted the folder in the timer slot, opening every file for the resolution and date-taken sorts. It then rebuilt the whole file tree (`setRootPath` reset, expanded-state save/restore, a recursive search-filter pass per `directoryLoaded`). While any soft delete was pending, the scan never matched the stored list, which leaves pending files out, so that full rebuild ran on every change. The rescan now runs in `FolderRescanWorker` on the thread pool, with a generation guard. It compares the scan without pending deletions, and re-reads the tree only when a file appeared (the tree's model drops removed rows on its own). (2) File > commit pending deletions ran `trash_batch` in the menu slot (about 0.27 s per shell call plus a stat per file). It now runs in `FileDeleteWorker` (`commit_pending_in_background`). The actions stay on the undo stack, marked `committing` so Undo skips them and a rescan does not resurrect them, and only they are dropped when the worker reports. A window closing mid-commit waits for it and settles it (`finish_pending_commit`).
- **Result / numbers**: 15 new tests (`tests/test_folder_rescan_worker.py`, `tests/test_trash_commit_background.py`), with fakes in place of the shell Recycle Bin. The folder refresh, folder poll, recycle bin, main-window layout and close suites pass.
